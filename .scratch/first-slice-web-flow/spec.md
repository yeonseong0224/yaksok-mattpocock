# 첫 슬라이스: 웹에서 약속 생성부터 확정까지

Status: ready-for-agent

## Problem Statement

여러 사람이 만날 날짜와 시간을 정하려면 단톡방에서 "언제 돼?"를 몇 번이고 주고받아야 한다. 누가 어떤 시간에 되는지 한눈에 볼 수 없고, 응답을 안 한 사람을 기다리다 결정이 늘어지며, 결국 누군가 임의로 정해 버린다. yaksok은 이 조율을 링크 하나로 끝내려 하지만, 지금은 연결 확인용 엔드포인트 하나만 있어 사용자가 할 수 있는 일이 없다.

## Solution

웹에서 "새 약속 만들기"를 누르면 초대 링크가 생긴다. 링크에서 처음으로 닉네임·PIN 등록에 성공한 사람이 방장이 되어 정원, 날짜 범위, 하루 시간 범위, 약속 길이, 마감 시각을 설정하고 모집을 시작한다. 다른 사람들은 같은 링크로 참여자 등록을 하고 30분 슬롯 단위로 가능 시간을 골라 제출한다. 모집 중에도 모두가 현재 후보를 실시간으로 보고, 마감 시각이 되거나 방장이 조기 마감하면 최종 후보(서로 겹치지 않는 최대 5개)가 공개된다. 방장이 후보 하나를 골라 확정하면 약속의 시작 시각이 정해진다.

카카오 챗봇 진입점은 다음 슬라이스다. 이번 슬라이스의 링크 발급은 웹에서만 한다.

## User Stories

### 약속 만들기와 방장

1. 약속을 잡고 싶은 사람으로서, 웹에서 "새 약속 만들기"를 눌러 초대 링크를 받고 싶다. 그래야 단톡방에 바로 공유할 수 있다.
2. 링크를 연 사람으로서, 아직 아무도 등록하지 않은 링크라면 닉네임·PIN으로 등록해 방장이 되고 싶다. 그래야 약속 설정을 시작할 수 있다.
3. 링크를 먼저 열었지만 등록은 늦은 사람으로서, 다른 사람이 먼저 등록에 성공했다면 "방장이 약속을 설정 중입니다" 화면을 보고 싶다. 그래야 방장이 둘이 되는 혼란이 없다.
4. 방장과 동시에 등록 버튼을 누른 사람으로서, 서버가 한 명만 방장으로 받고 나머지는 설정 중 화면으로 안내받고 싶다. 그래야 방장이 정확히 한 명으로 유지된다.
5. 설정 중 화면을 보는 사람으로서, 방장이 설정을 마치면 새로고침 없이 참여자 등록 화면으로 넘어가고 싶다. 그래야 다시 링크를 찾아 들어오지 않아도 된다.
6. 방장으로 등록한 사람으로서, 10분 안에 설정을 끝내지 못하면 설정 시간이 만료되었다는 안내를 받고 싶다. 그래야 왜 더 진행할 수 없는지 안다.
7. 설정 중 화면을 보는 사람으로서, 방장의 초안이 만료되면 내가 방장으로 등록할 수 있는 화면으로 넘어가고 싶다. 그래야 방치된 링크를 다시 쓸 수 있다.
8. 링크를 연 사람으로서, 발급 후 3개월이 지난 링크라면 만료되었다는 안내를 받고 싶다.
9. 링크 미리보기를 보는 사람으로서, 링크를 열기만 해도 약속이 만들어지거나 방장이 정해지지 않기를 바란다.

### 설정과 모집 시작

10. 방장으로서, 정원을 나를 포함해 2~30명 사이로 정하고 싶다(−/+ 버튼 또는 직접 입력).
11. 방장으로서, 월간 달력에서 시작일과 종료일을 클릭해 날짜 범위를 정하고 싶다. 오늘부터 고를 수 있고, 시작일과 종료일을 포함해 최대 90일이다.
12. 방장으로서, 약속 이름(1~30자)을 붙이고 싶다. 그래야 참여자들이 어떤 약속인지 알 수 있다.
13. 방장으로서, 하루 시간 범위와 약속 길이는 따로 고민하지 않아도 되길 바란다. MVP에서는 09:00~24:00과 2시간으로 고정된다.
14. 방장으로서, 설정을 마치면 초대 링크 화면에서 링크를 복사하고 바로 내 가능 시간을 입력하러 가고 싶다.
15. 방장으로서, 마감을 날짜와 시각(30분 단위)으로 정하고 싶다.
16. 방장으로서, 마감 기본값으로 "지금부터 24시간 뒤를 30분 단위로 올림한 시각"이 채워져 있길 바란다(날짜 범위 마지막 날 00:00보다 늦으면 그 직전 30분 경계).
17. 방장으로서, 마감이 지금으로부터 30분 미만이거나 날짜 범위 마지막 날 00:00 이후라면 거부당하고 그 이유를 보고 싶다.
18. 방장으로서, 필수 설정이 하나라도 빠지면 모집을 시작할 수 없길 바란다.
19. 방장으로서, 설정을 완료하면 약속이 모집 중으로 바뀌고 참여자들이 등록할 수 있게 되길 바란다.

### 참여자 등록과 로그인

20. 링크로 들어온 사람으로서, 모집 중인 약속에 닉네임과 숫자 4자리 PIN으로 참여자 등록을 하고 싶다. 전체 서비스 회원가입은 하고 싶지 않다.
21. 참여자로서, 닉네임에 이모지·기호·가운데 공백을 쓸 수 있고 1~10자(화면에 보이는 글자 기준)이길 바란다.
22. 참여자로서, 닉네임 앞뒤 공백은 자동으로 지워지길 바란다.
23. 참여자로서, `Chulsoo`와 `chulsoo`처럼 대소문자만 다른 닉네임은 다른 사람으로 취급되길 바란다.
24. 참여자로서, 같은 약속에 이미 있는 닉네임(탈퇴자 포함)으로는 등록할 수 없고 그 이유를 보고 싶다.
25. 참여자로서, 폭 0 공백 같은 보이지 않는 문자로 다른 사람 닉네임을 흉내 낸 등록이 거부되길 바란다.
26. 참여자로서, 정원이 다 찼으면 등록이 거부되고 그 이유를 보고 싶다.
27. 참여자로서, 마감됐거나 확정된 약속에는 새로 등록할 수 없길 바란다.
28. 참여자로서, 등록하면 바로 로그인되어 새로고침하거나 다음 날 다시 열어도 다시 인증하지 않고 싶다.
29. 참여자로서, 다른 기기나 브라우저에서 닉네임과 PIN을 입력해 같은 참여자로 다시 로그인하고 싶다.
30. 참여자로서, 여러 기기에서 동시에 로그인해 있을 수 있길 바란다.
31. PIN을 잊은 참여자로서, "다른 닉네임으로 새로 참여하세요"라는 안내를 보고 싶다.
32. 참여자로서, 로그아웃하면 이 기기의 로그인과 미제출 입력이 지워지길 바란다.
33. 참여자로서, 이 약속의 로그인 상태가 다른 약속에 영향을 주지 않길 바란다.
34. 참여자로서, 참여자 명단(닉네임과 방장 표시)을 보고 싶다.
35. 등록하지 않은 사람으로서, 약속의 상태만 볼 수 있고 명단·시간 정보는 볼 수 없길 바란다.

### 가능 시간 선택과 제출

36. 참여자로서, 날짜 범위 × 하루 시간 범위의 30분 슬롯 격자에서 드래그로 가능 시간을 고르고 싶다.
37. 참여자로서, 날짜 하나를 누르면 그날의 설정 범위 슬롯이 모두 선택되길 바란다.
38. 참여자로서, 큰 시간 블록을 누르면 그 안의 설정 범위 슬롯이 모두 선택되길 바란다.
39. 참여자로서, 일부만 선택된 날짜나 블록을 누르면 전체 선택, 전체 선택된 것을 누르면 전체 해제되길 바란다.
40. 참여자로서, 일부만 선택된 날짜나 블록은 전체 선택과 구별되는 모양으로 보고 싶다.
41. 참여자로서, 드래그가 끝날 때마다 선택이 이 브라우저에 자동 저장되어 새로고침해도 남아 있길 바란다.
42. 참여자로서, 제출하기 전의 선택은 나에게만 보이고 다른 사람과 후보 계산에는 반영되지 않길 바란다.
43. 참여자로서, 제출 버튼을 누르면 내 슬롯 전체가 서버에 저장되고 다른 사람 화면과 후보에 반영되길 바란다.
44. 참여자로서, 가능한 시간이 하나도 없어도 제출할 수 있고, 그때는 "모두 불가능으로 제출됩니다" 확인을 받고 싶다.
45. 참여자로서, 제출한 뒤에도 마감 전까지는 수정해서 다시 제출하고 싶다.
46. 참여자로서, 제출 후 수정 중에는 다시 제출하기 전까지 기존 제출값이 계속 집계에 쓰이고, 아직 제출하지 않은 수정이 있다는 표시를 보고 싶다.
47. 여러 기기를 쓰는 참여자로서, 다른 기기에서 더 최신 제출을 했다면 이 기기의 오래된 미제출 입력은 버려지고 최신 값과 함께 그 사실을 안내받고 싶다.
48. 여러 기기를 쓰는 참여자로서, 오래된 기준으로 제출하면 거부되고 최신 제출값으로 화면이 갱신되길 바란다.
49. 참여자로서, 지금보다 이전 시각의 슬롯은 지난 칸으로 구분되어 보이고, 제출에 섞여 있어도 무시되며 이미 저장된 지난 슬롯은 지워지지 않길 바란다.
50. 참여자로서, 마감된 뒤에는 내 입력을 볼 수만 있고 수정·제출은 할 수 없길 바란다.
51. 참여자로서, 마감 시각이 화면에는 아직 안 지났어도 서버 기준으로 지났다면 제출이 거부되길 바란다.
52. 참여자로서, 다른 참여자들의 제출 현황이 캘린더를 보는 동안 5초마다 갱신되길 바란다.
53. 참여자로서, 시간표에서 각 참여자는 시간마다 "가능" 또는 "불가능"으로만 보이고, 미제출자와 빈 제출자는 모든 시간에 "불가능"으로 보이길 바란다.
54. 참여자로서, 시간마다 가능 인원을 "3/5명"처럼 active 참여자 전체 대비로 보고 싶다.
55. 참여자로서, 모든 시각을 한국 시간으로 보고 싶다.

### 마감과 후보

56. 방장으로서, 마감 시각 전에도 조기 마감해 모집을 끝내고 싶다.
57. 참여자로서, 마감 시각이 지나면 누가 따로 누르지 않아도 약속이 마감된 것으로 보이길 바란다.
58. 참여자로서, 모든 참여자가 제출해도 자동으로 마감되지 않길 바란다.
59. 참여자로서, 모집 중에도 현재 제출값 기준의 후보를 실시간으로 보고 싶다.
60. 참여자로서, 마감 즉시 최종 후보를 보고 싶다.
61. 참여자로서, 후보는 약속 길이 전체에 걸쳐 2명 이상이 연속으로 가능한 시작 시각이길 바란다.
62. 참여자로서, 후보는 가능 인원이 많은 순, 같으면 시작이 빠른 순으로 보고 싶다.
63. 참여자로서, 14:00·14:30·15:00처럼 서로 겹치는 후보가 나란히 나오지 않고, 서로 겹치지 않는 최대 5개를 보고 싶다.
64. 참여자로서, 하루 시간 범위를 벗어나는 후보나 이미 지난 시각의 후보는 보이지 않길 바란다.
65. 참여자로서, 후보마다 참석 가능한 사람의 닉네임을 보고 싶다.
66. 참여자로서, 후보가 없으면 "2명 이상 겹치는 시간이 없어요"라는 안내를 보고 싶다.

### 확정

67. 방장으로서, 마감된 약속에서 표시된 후보 중 하나를 골라 확정하고 싶다. 히트맵에서 칸을 눌러 누가 가능한지 볼 수 있고, 그 칸이 표시 후보의 시작 시각이면 확정 버튼이 보인다.
68. 방장으로서, 모집 중에는 "일정 확정하기" 버튼 대신 "조기 마감" 버튼을 보고 싶다.
69. 방장으로서, 내가 본 뒤 상황이 바뀌어 고른 후보가 더 이상 유효하지 않으면(2명 미만이 됐거나 이미 지난 시각) 확정이 거부되고 새 후보 목록을 받고 싶다.
70. 방장으로서, 가능 인원만 바뀌었고 여전히 표시 후보라면 그대로 확정되길 바란다.
71. 참여자로서, 확정된 약속의 시작 시각과 끝나는 시각, 참석 가능한 사람을 보고 싶다.
72. 멤버로서, 확정·조기 마감·설정은 방장만 할 수 있길 바란다. 참여 링크만으로 방장 권한을 얻을 수 없어야 한다.

## Implementation Decisions

### 근거 문서

- 규칙의 1순위 기준은 비즈니스 규칙 문서이고 그다음이 ERD, API 명세, PRD 순이다. 이번 슬라이스의 결정은 규칙 문서에 "2026-11-06 그릴링 결정"으로 반영되어 있고, 요약은 미결·모순 목록 1-1절에 있다.
- 용어는 루트 GLOSSARY를 따른다(약속, 참여자, 방장, 멤버, 슬롯, 제출, 마감, 후보, 확정).
- ADR-0001: 마감 상태는 크론 없이 조회할 때 계산한다.

### 스키마

- 연결 확인용 임시 User 모델을 지우고, ERD의 테이블 5개(promise_links, promises, participants, participant_available_slots, participant_sessions)로 바꾼다. 마이그레이션은 `prisma migrate dev`로 만든다.
- ERD 4.1·4.2의 UNIQUE, FK(ON DELETE RESTRICT), CHECK 제약과 "방장은 약속당 한 명" 부분 UNIQUE 인덱스를 마이그레이션 SQL에 넣는다.
- 모든 시점 컬럼은 Timestamptz(3)이고, 하루 시간 범위는 SMALLINT 분 값이다.
- PIN 실패 제한 컬럼은 추가하지 않는다(MVP 결정).
- 연결 확인용 health 엔드포인트는 새 스키마 기준으로 고친다.

### 모듈

- **후보 계산 모듈(깊은 순수 모듈)**: 입력은 약속 설정(날짜 범위, 하루 시간 범위, 약속 길이), 제출을 마친 active 참여자들의 슬롯, 기준 시각이다. 출력은 순위가 매겨진, 서로 겹치지 않는 최대 5개 후보이며 후보마다 시작 시각, 끝 시각, 참석 가능한 참여자 목록을 담는다. DB와 시계에 의존하지 않는다. 규칙은 다음과 같다.
  - 시작 시각은 30분 슬롯 경계다.
  - 구간은 시작 포함, 끝 미포함이다.
  - 구간 전체가 하루 시간 범위 안에 있어야 한다. 자정 넘김은 00:00~24:00일 때만 생긴다.
  - 약속 길이 전체에 걸쳐 연속으로 가능한 참여자만 센다.
  - 2명 이상인 시각만 후보다.
  - 기준 시각 이전에 시작하는 후보는 뺀다.
  - 가능 인원이 많은 순, 같으면 시작이 빠른 순으로 정렬한다.
  - 정렬 순서대로 고르되, 이미 고른 후보와 겹치면 건너뛴다.
  - 후보 조회 API와 확정 API 모두 이 모듈을 쓴다.
- **유효 상태 계산**: DB 상태가 collecting이어도 서버 시각이 마감 시각 이상이면 closed로 보는 규칙을 한 곳에 둔다. 모든 조회는 이 값을 응답한다. 마감 이후 들어온 첫 쓰기 요청은 트랜잭션 안에서 DB 상태를 closed로 바꾸고 커밋한 뒤, 원래 요청에 맞는 결과(대개 409)를 돌려준다.
- **닉네임 정규화**:
  - 앞뒤 공백을 제거하고 NFC로 정규화한다. 대소문자는 바꾸지 않는다.
  - 길이는 grapheme 기준 1~10자다.
  - 제어 문자(Cc)와 서식 문자(Cf)는 거부한다. 단 ZWJ와 이모지 변형 선택자는 허용한다.
  - 표시용 nickname과 normalized_nickname 모두 앞뒤 공백을 제거한 값을 저장한다.
- **세션**:
  - 약속별 httpOnly 쿠키(`ys_session_{promiseId}`, Path는 해당 약속 API 경로)를 쓴다.
  - DB에는 토큰의 해시만 저장한다.
  - 만료는 마감 후 7일이다.
  - 로그아웃은 행을 지우지 않고 expires_at만 현재 시각으로 바꾼다.
- **PIN**: 숫자 4자리만 받고 해시로 저장한다. 실패 제한과 복구 기능은 없다.

### API 계약 (`/api/v1`, 기존 명세 기준)

| 동작                 | 엔드포인트                                           | 근거                                                     |
| -------------------- | ---------------------------------------------------- | -------------------------------------------------------- |
| 웹에서 링크 발급     | `POST /links` → inviteToken 반환                     | **신규**(명세 없음. 인증 없음, promise 행은 만들지 않음) |
| 링크 조회            | `GET /links/{inviteToken}`                           | MEMBER-API-01 (3개월 경과 시 410 `LINK_EXPIRED`)         |
| 방장 등록(약속 생성) | `POST /links/{inviteToken}/host`                     | MEMBER-API-02                                            |
| 약속 상태·설정 조회  | `GET /promises/{promiseId}`                          | STATE-API-01 (비로그인은 상태만)                         |
| 설정 완료·모집 시작  | `POST /promises/{promiseId}/start`                   | STATE-API-02                                             |
| 참여자 등록          | `POST /promises/{promiseId}/participants`            | MEMBER-API-03                                            |
| 로그인 / 로그아웃    | `POST`·`DELETE /promises/{promiseId}/auth/session`   | MEMBER-API-04 / 07                                       |
| 내 정보 / 명단       | `GET /promises/{promiseId}/me`, `GET …/participants` | MEMBER-API-05 / 06                                       |
| 가능 시간 제출       | `PUT /promises/{promiseId}/me/availability`          | TIME-API-01                                              |
| 가능 시간 현황       | `GET /promises/{promiseId}/availability`             | TIME-API-02 (`serverTime` 포함)                          |
| 조기 마감            | `POST /promises/{promiseId}/close`                   | STATE-API-04                                             |
| 후보 조회            | `GET /promises/{promiseId}/candidates`               | STATE-API 후보 조회                                      |
| 확정                 | `POST /promises/{promiseId}/confirmation`            | STATE-API-05                                             |

- 시각은 ISO 8601에 `+09:00`을 붙이고 밀리초 3자리로 표기한다. 하루 시간 범위는 응답에서 HH:mm 문자열로 표기한다.
- 모집 시작 요청이 받는 값은 약속 이름, 날짜 범위, 정원, 마감이다. 하루 시간 범위(09:00~24:00)와 약속 길이(2시간)는 받지 않고 서버가 기본값으로 저장한다(STATE-03-01 MVP 결정). 검증 규칙은 다음과 같다.
  - 약속 이름은 앞뒤 공백을 제거한 뒤 1~30자다.
  - 정원은 2~30명이다.
  - 날짜 범위는 오늘(KST)부터, 양 끝을 포함해 최대 90일이다.
  - 마감은 지금보다 30분 이상 뒤이고, 마지막 날 00:00(KST)보다 앞이다.
- 제출 API의 동작은 다음과 같다.
  - baseVersion이 다르면 409 `AVAILABILITY_VERSION_CONFLICT`를 반환한다.
  - 슬롯이 5,000개를 넘으면 422 `SLOT_LIMIT_EXCEEDED`를 반환한다.
  - 범위 밖 슬롯은 빼고 저장한다.
  - 지난 슬롯은 무시하고, 이미 저장된 지난 슬롯은 보존한다. 미래 슬롯만 전체 교체한다.
  - 제출 시각을 기록하고 version을 1 올린다.
- 확정 API는 closed 상태에서만 받는다. 후보 계산 모듈로 다시 계산해서 요청한 시작 시각이 표시 후보가 아니면 409와 새 후보 목록을 반환한다. 저장하는 값은 `confirmed_start_at`뿐이다.
- 권한 분리: 설정, 조기 마감, 확정은 세션의 참여자가 그 약속의 방장(role=host)인지 서버가 확인한다. 초대 토큰과 promiseId만으로는 어떤 권한도 얻을 수 없다.

### 동시성

- 쓰기 요청은 promises 행을 FOR UPDATE로 잠근 뒤, 잠금 후의 DB 시각(`clock_timestamp()`)으로 마감 여부와 10분 draft 만료를 판정한다(ERD 8장).
- 방장 등록이 동시에 들어오면 promise_link_id UNIQUE와 잠금으로 한 명만 성공한다. 진 쪽은 설정 중 응답을 받는다.
- 만료된 draft를 발견한 쓰기 요청은 세션 → 방장 참여자 → promise 순서로 명시적으로 삭제하고, promise_link는 미사용 상태로 남긴다.
- 조기 마감과 제출이 경합하면 잠금 순서로 직렬화한다. 먼저 잠금을 얻은 쪽이 이긴다.

### 화면

- **디자인 기준**: Figma 와이어프레임. 화면별 프레임과 티켓의 대응은 `docs/design/FIGMA.md`에 정리돼 있다. 와이어프레임과 이 스펙이 다르면 이 스펙을 따른다(아래 2026-11-09 결정).
- 사용자 흐름: 홈 "새 약속 만들기" → 링크 발급 후 바로 그 링크로 이동 → 방장 등록(닉네임·PIN) → 설정(약속 이름, 날짜 범위 달력, 정원, 마감) → 초대 링크 화면(복사, "내 가능 시간 입력하기") → 시간 투표 → 결과·확정.
- 페이지는 링크 진입 하나에서 상태에 따라 다른 화면을 보여준다.
  - 방장 등록
  - 설정 중 대기(폴링)
  - 방장 설정 폼
  - 초대 링크
  - 참여자 등록·로그인
  - 시간 투표(주간 7일 격자, 월·주 이동, 로컬 자동 저장, 제출, 5초 폴링)
  - 결과(히트맵, 시간 상세 팝업, 후보)
  - 확정 결과
- **와이어프레임과 다르게 구현하는 부분 (2026-11-09 결정)**:
  - 설정 폼에 하루 시간 범위와 약속 길이 입력란이 없는 것이 맞다. 값은 기본값으로 고정한다.
  - 안내 문구는 "최대 3개월"이 아니라 "최대 90일"이다. 마감 시각은 30분 단위로 고른다(23:59 아님).
  - 미응답 구분(명단의 "응답 완료", 상세 팝업의 "미응답 N명")은 MVP에서 표시하지 않는다. 가능/불가능만 보여준다(TIME-12-02).
  - 시간 상세 팝업의 "이 시간으로 확정하기"는 방장에게만, 마감 후에만, 그 칸이 표시 후보의 시작 시각일 때만 보인다.
  - 모집 중에는 "일정 확정하기" 자리에 "조기 마감"을 둔다.
  - 반복 기능(주간·특정 날짜 반복, 우클릭 메뉴)과 모바일 전용 시간 선택 화면은 이번 슬라이스에서 빼고 별도 티켓으로 둔다.
- 폴링은 SWR의 주기 조회로 한다. 캘린더가 보이는 동안에만 5초 간격으로 조회한다.
- 미제출 입력은 localStorage에 `약속ID+참여자ID` 키로 저장하고, 함께 기준 버전을 저장한다.

## Testing Decisions

- **좋은 테스트의 기준**: 외부에서 관찰할 수 있는 동작만 검증한다. HTTP 상태 코드, 응답 본문, 쿠키, 그리고 다음 요청에서 보이는 결과다. 내부 함수 호출이나 쿼리 모양은 검증하지 않는다. 테스트 이름은 GLOSSARY 용어로 쓴다.
- **도구**: Vitest를 새로 도입한다. 테스트는 CI에서도 돌아야 하므로 CI에 Postgres 17 서비스 컨테이너와 마이그레이션 적용 단계를 추가한다.
- **주 seam: HTTP API + 실제 DB**
  - Next 라우트 핸들러 함수에 `Request`를 직접 넣고 `Response`를 검증한다.
  - DB는 로컬 Docker Postgres 안의 별도 테스트 데이터베이스이며, 테스트마다 비운다.
  - 사용자 흐름 단위로 쓴다. 예: 방장 등록 → 모집 시작 → 참여자 둘 등록 → 제출 → 조기 마감 → 후보 조회 → 확정.
  - 마감이 지난 상황은 준비 단계에서 DB의 `voting_deadline_at`을 과거로 바꿔 만든다. draft 만료는 `created_at`을 과거로 바꿔 만든다. 시계를 주입하는 seam은 만들지 않는다.
  - 검증할 대표 사례:
    - 닉네임 정규화와 중복(409), 정원 초과
    - 권한: 멤버가 확정을 요청하면 거부
    - 버전 충돌, 마감 후 제출 거부와 상태 전환
    - 동시 방장 등록에서 한 명만 성공
    - 확정 재검증 409
- **보조 seam: 후보 계산 모듈 (순수 함수 단위 테스트)**
  - 자정 넘김(00:00~24:00), 하루 범위 초과 제외, 반열림 구간
  - 연속 가능 조건, 2명 미만 제외, 지난 시각 제외
  - 정렬, 겹치는 후보 건너뛰기, 5개 상한, 후보 없음
- **선행 사례**: 저장소에 아직 테스트가 없다. 첫 티켓이 테스트 하네스(Vitest, 테스트 DB 준비와 초기화, 라우트 핸들러 호출 도우미)를 만들고, 이후 티켓이 그 위에 테스트를 쌓는다.
- **UI**는 자동 테스트 대상이 아니다. 각 티켓의 화면은 브라우저에서 수동으로 확인한다.

## Out of Scope

- 카카오 챗봇 스킬 API와 챗봇에서 링크 발급(A-01). 5초 제한 검증도 함께 다음 슬라이스로 간다.
- 재설정(모집 중 설정 변경, 마감 연장·단축), 재조율(closed·confirmed → collecting)
- 약속 취소, 취소 복구
- 탈퇴, 내보내기, 방장 위임·승계, 정원 축소
- PIN 입력 실패 제한(MVP 이후 재검토), PIN 복구
- 기록 보관 기간과 삭제 정책
- EXCEPTION 규칙 전체(ERD 8장 이외의 예외 처리)
- 후보가 없을 때 방장의 후속 행동(RESULT-08-02)
- 해외 시간대 표시, 카카오 로그인, 톡캘린더, 장소 관련 기능 전부
- 방장이 하루 시간 범위와 약속 길이를 직접 정하는 기능(MVP는 기본값 고정)
- 가능 시간 반복 기능(주간·특정 날짜 반복, 우클릭 메뉴), 모바일 전용 시간 선택 화면(선택·스크롤 모드, 바텀시트). 별도 티켓: `.scratch/vote-ui-extras/issues/`
- 미응답 표시(명단의 응답 완료 여부, 상세 팝업의 미응답 수)

## Further Notes

- 웹 링크 발급 엔드포인트는 API 명세에 없어서 이번에 새로 정의한다. 누구나 호출할 수 있으므로 남용될 수 있지만, MVP에서는 제한하지 않는다.
- PIN 실패 제한이 없어서 4자리 PIN은 자동 대입에 약하다. 알고 내린 결정이며 MVP 이후 재검토한다.
- PIN을 잊은 참여자의 기존 행은 active로 남아 정원을 차지한다. 내보내기 슬라이스에서 해결한다.
- 미결·모순 목록의 X-07(TIME-11-02 내부 모순)은 재제출 필요 상태에서만 문제가 되는데, 재제출 필요 상태는 재설정으로만 생긴다. 이번 슬라이스에는 재설정이 없으므로 영향이 없다.
- Next.js 16은 기존 지식과 다른 부분이 있으므로 구현 전에 `node_modules/next/dist/docs/`의 해당 가이드를 읽는다(AGENTS.md).
